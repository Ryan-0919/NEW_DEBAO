## 5. 发现的问题

### 问题1：第3小问有遗漏点但没有错误标注

第3小问存在 2 个遗漏点，但 `wrongMarks` 为 0。  
这说明现在的提示词和校验还不能稳定要求“有遗漏点时必须尽量找到对应错误或不足位置并打错号”。

影响：学生端看到遗漏点，但正文中可能没有红色错号定位，批改体验不够直观。

建议：继续强化阶段1提示词和后端校验。尤其是要求 AI 对“遗漏法律后果、遗漏前提条件、主体/责任关系没有说完整”也生成 `wrong` 或 `missing` 类局部标注。

### 问题2：存在 2 个空 highlight

本次统计到 `emptyHighlights = 2`。  
主要出现在阶段2返回的标注定位中，有些 mark 没有找到原文片段。

影响：前端可能无法正常划线，或者出现有评语但无划线的情况。

建议：阶段2如果找不到原文，不应该返回空字符串；应要求返回最接近的原文短句，或者后端校验失败并重试阶段2。

### 问题3：点评字数略超预期

当前希望每问点评控制在 300-400 字左右。本次：

| 小问 | 点评字数 |
| --- | --- |
| 小问1 | 463 |
| 小问2 | 391 |
| 小问3 | 405 |

小问1明显偏长，小问3略超。  
建议：后台提示词里把“300-400字”进一步收紧成“280-380字，严禁超过400字”。

### 问题4：AI仍会返回 markdown 代码块

阶段1多次返回了 ```json 代码块。当前解析器可以兼容解析，所以本次没有失败。

影响：暂不影响落库，但说明模型仍没有完全遵守“只返回纯 JSON”的要求。

建议：保留代码块解析兼容，同时继续在提示词中强调不要输出 markdown。

### 问题5：日志 totalTokens 统计可能不准

日志中：

| 字段 | 值 |
| --- | --- |
| promptTokens | 16722 |
| completionTokens | 4606 |
| totalTokens | 16722 |

`totalTokens` 理论上应接近 `promptTokens + completionTokens`。  
这里显示为 16722，疑似聚合 usage 时 total_tokens 没有正确累加。

影响：不影响批改结果，但影响后续成本统计和性能监控。

建议：单独修正 V2 usage 聚合逻辑。

## 6. 结论

这张真实试卷 V2 批改链路整体可用：

- 能走 V2，不再走 V1。
- 能使用后台策略配置的模型 `claude-opus-4-8`。
- JSON 解析成功。
- 三个小问全部批改完成。
- 得分为 10 / 15。
- 正向得分标注合计 10 分，与总分一致。
- 有错误标注、有遗漏点、有自然语言点评。
- 本次测试没有覆盖正式学生记录。

但上线前建议继续修 3 个质量点：

1. 有遗漏点但没有错号时，应强制补一个局部错误/不足标注。
2. 阶段2不允许返回空 highlight。
3. 修复 V2 usage 的 `totalTokens` 统计。
